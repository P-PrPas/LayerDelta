# E7s: can Antigravity be driven headless for the benchmark? (spike result)

Owner: AI Engineer · Date: 24 Nov 2026 · Gates: E7b · Design: [v0.5 §5.2 and §5.5](../architecture/v0.5-evaluators-benchmark.md)

**Verdict.** Items (i), (iii) and (iv) pass with evidence. Item (ii) passes with a workaround (MCP configuration is global, so sessions run one at a time). Item (v), isolation, **fails with the host's own flags**: in a headless session the agent read a file outside its directory and fetched a URL from the network, with `--sandbox` set. Isolation therefore needs a dedicated OS account and a network block, which needs the owner (a second Antigravity login), or the benchmark runs with **audit-only** isolation and reports the violation rate (design §5.2). Items (vi) and (vii) are partly verified and listed below. The decision for the owner is at the end.

## What was run

The `agy` CLI (version 1.5.16, `C:\Users\peera\AppData\Local\agy\bin\agy.exe`) was run three times as real sessions in empty directories under `%TEMP%`: two one-word prompts (one with `USERPROFILE` and `HOME` redirected) and one three-step tool task. No benchmark data, no LayerDelta workspace and no secret was involved. The one thing not run: `--dangerously-skip-permissions`. This environment's safety classifier refused to launch an agent with all permission prompts off, and unattended benchmark sessions need an explicit owner decision about it (see the end). The sessions are stored in `~/.gemini/antigravity-cli/conversations` (the CLI's default).

## The seven questions

**(i) Launch non-interactively with a prompt and a working directory: yes.** `agy -p "<prompt>" --model gemini-4-hydrogen-high --effort high --output-format stream-json --print-timeout 120s`, run with the session directory as the working directory. It exits 0 and prints one JSON object per line. `--input-format stream-json` (one message per line on stdin) is the multi-turn form. Evidence: the `init` event's `cwd` was the directory it was started in; a one-word prompt took 7.2 s wall time.

**(ii) Per-session MCP configuration and permissions: partly.**
- *MCP.* `agy mcp add|remove|list|enable|disable` edits one global configuration: `agy mcp list` printed "No MCP servers configured" before and the file is shared by every session of this user. A session cannot carry its own servers on the command line. Workaround: arm L's driver runs `agy mcp add layerdelta -- layerdelta-mcp --connection <session>/connection.json` before the session and `agy mcp remove` after it, and sessions run **one at a time** (see vii). `--settings '<json>'` takes "settings.json keys for this session only, never saved"; whether an MCP server can be named there was not tested (the key names are not documented in `--help`), and it is the first thing E7b should try because it would remove the add/remove step.
- *Permissions.* The `init` event reports `permission_mode: "request-review"`. `--mode auto` printed "warning: --mode auto is not available for this account; continuing in the default mode". Even so, in print mode the tool calls of the tool task ran without any prompt (a shell command, a file read, a second shell command). So an unattended session does run its tools; what was not established is whether that comes from print mode itself or from the account. Permission rules exist in the product (changelog: `command(...)`, `mcp(server/tool)` allow, ask and deny rules), but I did not find their configuration format; E7b should get it from the settings file the CLI writes.

**(iii) Model and effort per session: yes.** `agy models` lists `gemini-4-hydrogen-low|medium|high|xhigh` among others; `--model gemini-4-hydrogen-high` was accepted and echoed in `init.model`, and `--effort` takes `low|medium|high|xhigh|max`.

**(iv) Transcript with tool calls and file reads, and token counts: yes.** `--output-format stream-json` emits: `init` (model, cwd, the list of 60 tools, permission mode), a `step_update` for every step (`user_input`, `agent_response`, `tool`) and a final `result`. A `tool` step has `tool_name` (for example `run_command`, `read_file`), its `parameters` (`CommandLine`, `Path`), its `output` and `duration_seconds`. An `agent_response` step has `usage {input_tokens, output_tokens, thinking_tokens, cache_read_tokens, total_tokens}`, and `result.usage` is the session total. So the transcript audit of design §5.2 (reads outside the session directory, network use, training code) can be done from this stream, and tokens (completion, thinking, total, cache reads) are exported. Cost note: a one-word prompt used 16,180 tokens, almost all of it the tool and system prompt, so the fixed cost per session is about 16k tokens before the task.

**(v) Run under another OS user or in a sandbox: the host's flags do not isolate; an OS account was not tried.**
- Task run (`--sandbox`, `--mode auto` unavailable, the default mode): the agent was asked to run `python -c "print(1+1)"`, to read `C:\Users\peera\AppData\Local\Temp\e7s-outside\holdout.txt` (a file I created outside the session directory) and to run `curl -sI https://example.com`. Result: the file's content (`outside-secret-123`) was returned to the model; the first `curl` failed in PowerShell (an alias of `Invoke-WebRequest`), `curl.exe` failed once in the sandbox (exit 1, no output) and, on the next attempt, ran and returned `HTTP/1.1 200`. The tool list also includes `search_web`, `read_url_content` and sixteen `browser_*` tools.
- Configuration cannot be redirected by environment: running with `USERPROFILE` and `HOME` pointing at an empty directory still worked and created nothing there, so the CLI finds `~/.gemini/antigravity-cli` through the OS profile, not the environment. A second profile means a second OS user.
- The changelog says the terminal sandbox is not available on every Windows host ("machines without an OS sandbox"); this host behaved as if it were not enforcing.
- Consequences for design §5.2: reading outside the session directory and downloading the public MNIST test set (which contains the holdout images) are possible for **both** arms with the host's flags alone. Prevention needs (a) a dedicated low-privilege Windows account for sessions (the owner must log that account in to Antigravity once), with only the session directory readable, and (b) an outbound firewall rule for that account that allows only the model provider's hosts. Not tried here: it needs an account, an interactive login and a firewall change on the owner's machine.

**(vi) Stop on limits and kill the process tree: partly.** `--print-timeout` exists (a turn limit; not exercised to its limit). There is no step or token limit flag, but the stream reports every step and its usage as it happens, so the driver can count steps and tokens and kill the process on a limit. The driver must kill the whole tree (`taskkill /F /T`), because `run_command` starts shells. Not exercised.

**(vii) Concurrency: serial only.** The conversation store, the MCP configuration and the settings are global to the OS user. Two sessions at once would share them. The driver runs one session at a time (the cost is wall time: the tool task took about 75 s for three commands).

## Findings that change the plan

1. **Isolation is the open problem, not the driver.** The driver can be written now (i, iii, iv work). Without an OS account and a firewall rule, every R session can read the machine and fetch MNIST, so the benchmark would be audit-only, and the audit would find the violations only after they happened.
2. **Auto-approval.** Unattended sessions ran tools in print mode in the default mode. If the owner wants prompts off explicitly (`--dangerously-skip-permissions`) it is their decision, and with no isolation it also lets an agent run any command as the benchmark user.
3. **Tools outside the experiment.** Both arms have `search_web`, `read_url_content` and browser tools in the tool list. Whether they can be turned off per session (a deny rule in `--settings`) is untested. They bypass any network rule that only restricts shell commands, so they must be disabled or blocked at the account level too.
4. **Fixed overhead.** About 16k tokens per session before the task, identical for both arms except for L's MCP tool schemas.

## Decision for the owner

1. **Isolation:** (a) create a dedicated low-privilege Windows account for sessions, log it in to Antigravity once, and allow outbound traffic only to the model provider (prevention); or (b) accept audit-only isolation and report the violation rate per arm (the design's fallback). (a) costs about a day of setup and your login; (b) costs validity if sessions download MNIST.
2. **Unattended approval:** allow `--dangerously-skip-permissions` for benchmark sessions (needed unless permission rules can be configured per session), only together with (a).

If you choose (a), E7b starts with a second spike on that account (items v and vi for real), then the driver. If you choose (b), E7b starts now and the design states that isolation is audit-only.

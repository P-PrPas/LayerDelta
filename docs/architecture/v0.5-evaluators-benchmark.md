# v0.5 design: evaluators as agent tools, and the research benchmark

Status: design for review · Tasks E1–E10 are on the [v0.5 board](../roadmap/Implementation_Plan_v0.5.md) · Milestone goal and acceptance in the [Roadmap](../roadmap/Roadmap.md#v05--evaluators-as-agent-tools--research-benchmark) · Questions for the owner: Q3 and Q4 in [QUESTION.md](../../QUESTION.md).

## 0. Goal and non-goals

**Goal.** After v0.4, an agent can read, plan and apply weight edits on any family, but it cannot measure what an edit did. The only measurement LayerDelta has is the v0.1 MNIST run (`propose → run → compare`), which is hardwired to `ReferenceCNN`. v0.5 adds layer C of the [target architecture](Architecture_Target.md):
- run a checkpoint on data;
- score it with a task evaluator: classification, segmentation, detection or OCR;
- probe or edit activations at a graph node;
- expose all of it as agent tools, with the same budgets, egress classes and trace as v0.4.

With that in place, v0.5 runs the experiment that v0.4 left open (Roadmap risk R1): **does seeing weights help an agent choose better edits?** The answer is a pre-registered benchmark on at least three families. A null result is a valid result.

**Non-goals.**
- Training or fine-tuning. Evaluators only run forward passes.
- Arbitrary user code for data. Datasets are declarative: a manifest, a known format and a preprocessing spec. There are no Python loaders.
- Bit-exact GPU replay. The replay criterion is the per-sample predicted class (or decoded string, or box set after matching) and the counts that come from it.
- Desktop work beyond supervision. The session viewer shows evaluation and probe events. Evaluation editing UI is v0.6.
- Publishing the benchmark result. The report is internal until the owner decides; see *Release readiness*.

## 1. Execution: running any attached graph

An evaluation needs a forward pass of the **child** weights through the parent's architecture. v0.3 already gives every checkpoint with a graph a provider and a mapping from graph parameters to checkpoint tensor names (graph IR `param` bindings, ties included). v0.5 adds an **executable artifact** to each attachment.

| Provider | Executable artifact | Made by | Runs user code at evaluation time? |
|---|---|---|---|
| `builtin` | the registered module class (in-tree; the corpus and `ReferenceCNN`) | nothing to store | No (in-tree code) |
| `torch_export` | the `ExportedProgram`, saved as `.pt2` by the G6 export worker during the human-triggered attach. This is new: G6 writes only `ir.json` today | the isolated export worker | The user's Python source does not run. Loading the file unpickles, though (rule 3) |
| `onnx` | the ONNX file the person attached | the person | No (`onnxruntime`, new optional extra `layerdelta[eval-onnx]`) |

Rules:
1. **Weights are substituted by checkpoint name.**
   - The evaluator loads the child safetensors and binds each graph parameter to the tensor that the graph IR names.
   - A parameter with no binding, or a shape or dtype mismatch, fails with `executable_mismatch`, before any forward pass.
   - Persistent buffers (BN running statistics) are bound the same way.
   - Lifted tensor constants and non-persistent buffers exist in the `.pt2` or ONNX file but not in the checkpoint. They are not editable. They are taken from the artifact, and their hash is part of the fingerprint.
2. **Every forward pass runs in a child process.** This uses the `job.py` / `process.py` pattern of v0.1: a job record, a spawned worker, a report file and recovery on restart. The API process never runs a model. The `torch_export` and `onnx` artifacts are loaded only in that worker.
3. **`.pt2` loading unpickles: it has the same trust as the attach.** In torch 2.6, `torch.export.load` calls `torch.load(..., weights_only=False)` on the state-dict and constants inside every `.pt2`. It is **not** pickle-free (verified on PR #70). The rules are therefore:
   - (a) Only the export worker writes the `.pt2`, at the human-triggered attach. The attachment record stores its SHA-256 and the torch version.
   - (b) The file is loaded only inside the evaluation worker: scrubbed environment, size caps and timeout, as `run_worker`. The worker re-hashes the file before loading it and refuses `executable_mismatch` on a hash or torch-version difference.
   - (c) **Residual risk:** the pickle comes from the same user code that the person already opted into running at attach (Q1 option 3, R4). An agent can trigger the *load* of an artifact a person made, but can never supply or change one.

   A documented fallback that is **not** in E1's scope: replay the graph IR with an in-tree interpreter of ATen ops. It avoids pickle entirely, but only covers the ops LayerDelta implements.
4. **Batch size.** An export with zero example inputs of one fixed shape is batch-specialised. E1 decides one of two options and records the choice in the attachment:
   - export with `dynamic_shapes` on dim 0;
   - evaluate at the exported batch size, padding the last batch and trimming its outputs.
5. **`onnxruntime` is a second ONNX parser.** It loads the file only in the evaluation worker, and the G7 limits (512 MiB, static shapes) apply.
6. **ONNX graphs keep BN unfused.** G7 attaches ONNX files whose initializers map to checkpoint names. A file whose BN is folded into conv cannot be bound (rule 1), so an evaluation of such a file is refused with `executable_mismatch` and the hint "export with `do_constant_folding=False` and training=PRESERVE".
7. **Fingerprint.** `evaluation_fingerprint` = hash of the evaluator spec, dataset split hash, preprocessing spec and its implementation version, executable artifact hash (constants included), torch version, device and dtype. Baselines are cached by `(checkpoint sha, fingerprint)`, as v0.1 does.

## 2. Datasets

A dataset is a **human-only import**, like a checkpoint. Agents choose among registered datasets; they never name a path.

```
POST /dataset-imports  {path, format, task, preprocessing, split_policy}      human only, 202 job
GET  /datasets, /datasets/{dataset_id}                                        model:read, tool `list_datasets` / `get_dataset`
```

- **Manifest.** The import writes a content-addressed manifest: one row per sample with `sample_id`, file SHA-256, label reference, `split` and optional `condition`. The v0.1 MNIST manifest (`data.build_manifest`) is the template and becomes dataset `mnist-v1` unchanged.
- **Formats (closed set).** `image-folder-labels` (classification: image files plus a CSV of labels); `image-mask` (segmentation: image plus an index-PNG mask); `image-boxes` (detection: a COCO-style JSON subset of `images`, `annotations` (bbox, category_id) and `categories`); `image-text` (OCR: image plus a text line). A new format is a code change in `src/`, with no model-specific code (the `test_no_model_specific_code_in_src` rule stays).
- **Preprocessing (declarative, one implementation).** This is how the roadmap risk "datasets still need model-specific code" is answered: what differs per model is data, not code. A model that needs more than this list is out of scope for v0.5 and is recorded as a gap.
  - **Steps, in a fixed order:**
    - `resize {size, mode: nearest|bilinear, antialias}`;
    - `resize_height {height, keep_aspect: true}` (CRNN-style OCR: T depends on width);
    - `pad_to {size, value, anchor: top_left|center}`;
    - `grayscale`;
    - `channel_order`;
    - `scale`;
    - `mean/std`.
  - **One implementation:** `torch.nn.functional.interpolate`. PIL resampling is never used, because pixels differ across libraries and versions. The implementation version is in the fingerprint, so V9 cannot break silently on an upgrade.
  - **Labels follow the same geometric steps:**
    - masks: nearest-neighbour resize and pad with the ignore index;
    - boxes: scale and offset, clip, and drop boxes that become empty;
    - OCR text: unchanged.
  - **Decoding runs on untrusted bytes:**
    - a closed list of decoders: PNG and BMP through Pillow, pinned in the `eval` extra. There is no JPEG in v0.5, because JPEG decoders differ by libjpeg version;
    - a pixel cap (`MAX_IMAGE_PIXELS`);
    - decoding happens only in the evaluation worker. Import checks hashes and headers only.
  - **`limit_samples: n`:** the first n samples of the split in `sample_id`-hash order. The subset is deterministic, and its hash is in the fingerprint.
- **Splits.** `exploration` and `holdout` are fixed at import by a stratified hash of `sample_id` (the v0.1 `stratified-hash-half-v1` rule) and stored as split hashes. Agents can evaluate only `exploration`. `holdout` is reachable only through the human-only final evaluation (§3.3).
- **Images never leave through agent tools.** Results refer to samples by `sample_id`, label and condition. No route returns pixels to an agent token. Humans see pixels in Desktop.
- **Synthetic datasets for oracles and the benchmark (no licence needed).** Generators in `tests/` and `tools/` make seeded datasets:
  - `shapes-seg`: discs, squares and triangles on noise, with masks;
  - `boxes-det`: the same shapes with boxes;
  - `glyph-ocr`: digit strings drawn from a 5×7 bitmap glyph table defined in the repo, with blur and noise conditions.

  They are imported through the same human route, so the import path is tested too. Real datasets (VOC, COCO, IAM and similar) need a licence decision: Q4.

## 3. Evaluators

### 3.1 Plugin shape

An evaluator is `(task, output decoder, metric)`. It is registered in-tree and has a version. It does not know any model.

| Task | Model output contract | Decoder | Metrics (primary first) | Per-sample record |
|---|---|---|---|---|
| `classification` | logits `[N, C]` | argmax | accuracy; confusion pair rate (`truth → confused_with`, the v0.1 metric); per-class recall | predicted class |
| `segmentation` | logits `[N, C, H, W]` | argmax per pixel, resized to the mask by nearest neighbour | mIoU; Dice; per-class IoU. A class absent from both prediction and truth in a sample is excluded from that sample's mean | per-class pixel counts |
| `detection` | boxes before NMS `[N, K, 4 + 1 + C]` in a declared box format (`xyxy` or `cxcywh`, absolute or relative) | score threshold, then class-wise NMS (in-tree, IoU 0.5 by default) | mAP@0.5; mAP@0.5:0.95 (COCO 101-point interpolation) | kept boxes |
| `ocr` | per-step logits `[T, N, A]` or `[N, T, A]` (declared) | CTC greedy decode with the declared blank index and alphabet | CER; WER; exact-match rate | decoded string |

- **Model output contract.** Anything a model needs to reach that contract, such as anchor decoding, must be inside the exported graph. NMS is outside, because `torch.export` cannot export data-dependent control flow. This matches the Roadmap mitigation of exporting only the backbone and neck plus the static head.
- **Evaluator spec.** `{task, version, decoder args, metric args, confusion pair (classification only)}`. Its hash is part of the fingerprint.

### 3.2 The evaluate tool

```
POST /checkpoints/{checkpoint_id}/evaluations   tool `evaluate`  capability eval:run  key=True  pure=False   → 202 {evaluation_id}
GET  /evaluations/{evaluation_id}                tool `get_evaluation`  (status, metrics, comparison)
GET  /evaluations/{evaluation_id}/changes        tool `evaluation_changes`  (paged per-sample changes)
```

- **Input.** `dataset_id`, `evaluator` (spec or a registered name), `split` (only `exploration` is allowed for an agent), `baseline` (default: the checkpoint's parent from S6 lineage; `null` gives absolute metrics only; a checkpoint with no parent, such as an import, gets `no_baseline` unless `baseline` is given explicitly), optional `limit_samples`, and optional `intervention` (§4.2).
- **Result.** Metrics for the checkpoint and the baseline on the same samples. The paired difference for each metric has a 95% paired-bootstrap interval with a fixed seed: 2,000 resamples, deterministic for a given fingerprint.
  - **Each metric** is `{name, primary, unit: rate|count|score, better: higher|lower, baseline, value, delta, ci: [lo, hi] | null}`. `per_class` rows have the same shape.
    - `delta` is always `value − baseline`. `better` gives the direction.
    - A `rate` may be unbounded above: CER and WER can exceed 1.
    - `unit` and `better` come from the metric's definition in the evaluator spec.
    - `ci` is null when the server cannot give one, for example too few samples in a class.
  - **Counts** of fixed, broken and changed samples.
  - **Job fields:** `status`, `created_at`, `started_at`, `finished_at`, `error_code`, `message`.
  - **Links:** the `evaluation_fingerprint` and `diff_hint`-style links to both checkpoints.
- **Changes.** Samples whose per-sample record changed. Each has `sample_id`, label, condition, before and after, `category`, `score_before` and `score_after`, paged like v0.1 `/changes`, with a sort option by score change. No pixels.
  - **Correctness.** Each task defines "correct" with a predicate in the evaluator spec, which is part of the fingerprint:
    - classification: argmax == truth;
    - OCR: exact string match;
    - segmentation: sample mIoU ≥ 0.5;
    - detection: every truth box is matched at IoU 0.5, with no false positive.
  - **Category:** `fixed` = incorrect → correct; `broken` = correct → incorrect; `changed` = the record changed and correctness did not.
  - **Per-sample score:** 0/1 accuracy, sample mIoU, F1@0.5 for detection (per-image AP is ill-defined with few boxes), or CER. The score's `better` direction is reported with it, so sorting by score change means "worst change first" for every task.
  - **Edge cases (pinned in the evaluator spec, shared by E3 and E4):**
    - a segmentation sample with no class in either truth or prediction is correct, with score 1.0;
    - a detection image with no truth and no predictions is correct, with F1 1.0;
    - detection matching is greedy by descending score, class-wise, and one-to-one.
  - **Detection boxes** are returned in source-image coordinates, mapped back through the inverse of the geometric preprocessing.
  - **OCR:** before and after are decoded strings: model output on exploration samples only, the same for both benchmark arms.
- **Budgets (extends v0.4 S3).** `evals` counts evaluation jobs. `eval_samples` counts forward passes, the baseline included unless it is a cache hit. Both are charged at submission, before any work, and refused with `budget_exhausted`. A repeated `key` is charged once, as with `apply`.
- **Trace.** Every evaluate and probe is a trace event with `checkpoint_id`, `evaluation_id`, dataset, split hash, fingerprint and the charge. It is linked to the apply that made the checkpoint, so the viewer can show a whole read → plan → apply → evaluate chain.
  - **Event fields:** `baseline_id`, `baseline_cached` and `links.apply_seq` to that apply. The trace stays ID-only (T5):
    - an intervention is stored in a human-only table, like `selections`, and the event carries only its `intervention_id` (a hash) and numeric counts, because graph node IDs carry module names;
    - the dataset appears only as its content-addressed `dataset_id`, never a name.
  - **Result reads** (`get_evaluation`, `evaluation_changes`, `get_probe`) carry the ID and the page offset.
  - **Result reads are scoped.** For an agent token they return only evaluations on `split: exploration` and probes made by that same session. Anything else answers `not_found`. A person's holdout final evaluation, or a class-2 probe a person ran, is therefore never readable by ID through an agent token (V3, V5). A person reads everything.
  - **Budgets:** `summary.budget` reports `evals` and `eval_samples`.
- **Human-only sample routes** for the supervision viewer (E9, [session-evaluations.md](../design/session-evaluations.md)):
  - `GET /datasets/{dataset_id}/samples/{sample_id}/image` returns the stored source file;
  - `.../label` returns the mask, boxes JSON or text line.

  Both serve the file safely:
  - the file is read only from the manifest's content-addressed store, never the original import path;
  - its SHA-256 is re-checked against the manifest;
  - the Content-Type comes from the manifest's format: PNG or BMP, `application/json` for boxes, `text/plain` for OCR text (Desktop renders it as text, never HTML);
  - the headers are `X-Content-Type-Options: nosniff` and `Content-Disposition: inline` with a fixed filename;
  - the size is bounded by the import cap;
  - the server never decodes the file. Both are refused (403) for every agent token, and both are in the V3/V5 route walk. A person may see holdout samples: the holdout gate is on agents.
  The model-input view (the preprocessed tensor) is deferred to v0.6.
- **Legacy MNIST routes stay.** `/runs`, `/comparison` and `/changes` keep their payloads but are reimplemented over the `classification` evaluator on `mnist-v1` with `ReferenceCNN` as a builtin. Acceptance V1 requires the outputs to be byte-for-byte unchanged.

### 3.3 Holdout gating (generalised from v0.1)

`POST /final-evaluations` stays human-only. It generalises from an MNIST recipe to any `(checkpoint, dataset, evaluator)`:
- The person confirms the **frozen recipe hash** of the child.
- The job evaluates the `holdout` split.
- The result goes into the existing holdout audit.

An agent token gets `forbidden` for `split: "holdout"` everywhere. A route walk test, extended from v0.2-T4, proves that no agent route returns holdout data, including through `changes`, the trace and the baseline cache.

## 4. Activation probe and activation edit at graph nodes

### 4.1 Probe

```
POST /checkpoints/{checkpoint_id}/probes   tool `probe`   capability weights:read + eval:run   key=True   → 202 {probe_id}
GET  /probes/{probe_id}                     tool `get_probe`  (status and the aggregates, `skipped_small` included; the same payload for a person; not in the structure-only profile, refused on the server)
```

- **What it records.** The tool runs up to `limit_samples` exploration samples and records the output of the graph nodes named by `node_id` (v0.3 G4 node ids), or the units of a group selector (`{"group": gid}`, which resolves to the group's `out_unit` node).
- **What it returns.** Per-unit aggregates over samples and spatial positions: mean, std, l2, the fraction of positive values, and optionally a histogram. These can be split by label or condition.
- **Activations derive from weights.** With known inputs, they recover weights algebraically (Roadmap R2). Therefore:
  - a probe needs `weights:read`;
  - class 1 applies the v0.4 S4a.2 rule (every statistic aggregates at least K elements, `aggregate_too_small`, `skipped_small`). For a probe, K counts samples × spatial positions per unit, so `limit_samples: 1` on a dense layer is refused;
  - raw activation tensors need `weights:values` (class 2).

  The control arm of the benchmark has no `weights:read`, so it has no probe either.
- **How it is implemented, per provider.**
  - `builtin`: forward hooks.
  - `torch_export`: the `GraphModule` from `ExportedProgram.module()`, with an extra output on the node.
  - `onnx`: the node output is added to the graph outputs in memory.

  A node a provider cannot reach, or a group that does not resolve to a reachable node, returns `probe_unsupported` with the reason. It is never answered silently with partial data. `probe_unsupported`, `no_baseline` and `executable_mismatch` go into the error catalog (S2 format) in E4 and E5.

### 4.2 Activation edit (in an evaluation, no child)

`evaluate` accepts an optional `intervention`: `{node_id | group, units, op: zero | scale, factor}`, applied at run time. This generalises v0.1's activation mode to any graph. No checkpoint is created. The evaluation is fingerprinted with the intervention, and the intervention is in the trace. It needs `eval:run` and `weights:read`, because it is a probe by another name: ablating a unit and watching the output change reveals how that unit acts. It is a measurement tool. A lasting edit is still a weight edit through `plan`/`apply`.

## 5. The research benchmark

### 5.1 Question and hypothesis

- **H1.** Under equal budgets, an agent that can read weight statistics (arm **W**) reaches a higher holdout repair score than the same agent without weight reads (arm **C**).
- **H0.** There is no difference. Reported as a result if it holds.
- **Scope of the claim.** The families, tasks, edit operations, budgets, provider and model that were tested. Nothing wider (as in the original [spec](../history/LayerDelta_Agent_Extension.md) §3.5).

### 5.2 Arms: one capability apart

| | Arm W | Arm C |
|---|---|---|
| Tools shared | `session_info`, `describe` (structure), `graph`, `groups`, `plan`, `validate`, `apply`, `diff` (status only, no statistics), `evaluate`, `get_evaluation`, `evaluation_changes`, `trace` | same |
| Weight reads | `stats`, `query`, `probe`, and an intervention in `evaluate` (class 1: aggregates only) | none: tools are **absent** from the tool list, not refused |
| Budgets | identical `applies`, `evals`, `eval_samples`, agent steps, completion tokens and wall time. The `scan` budget only matters to W | same |
| Provider, model, temperature, system prompt | identical, except that the tool list differs | same |

- **Token accounting.** W's tool schemas are longer, so prompt tokens differ by design. The budget limits completion tokens and steps. Total tokens (prompt + completion, cache reads included) are counted the same way for both arms and reported. Both rules are pre-registered.
- **The control arm must be clean. The server enforces it.** In v0.4:
  - `plan` and `validate` need `weights:read`;
  - `plan` returns `changed_elems`, `touched_elems`, `before_sha`, `after_sha` and `noop` (`edit.py`);
  - `diff` returns changed-element counts;
  - the no-op refusal of `apply` is itself a value oracle: scale a unit by 1.0 and the answer reveals whether it is all zero.

  Task E6 adds a **structure-only** profile for a token without `weights:read`:
  - plan, validate, apply and diff are allowed;
  - the fields above are stripped, and `diff` returns status only;
  - the no-op refusal is disabled (`allow_noop` is forced true) **for both arms** in the benchmark, so the arms behave the same.
- **Enforcement comes from the token's capabilities on the server, never from the tool list.** W's tools are absent from C's tool list (the UX layer) **and** refused for C's token. `execute` and the legacy MNIST tools are absent and refused for both arms.
- **V8 allow-lists fields per route.** The route walk asserts the exact set of field names each route returns to a C token, rather than deny-listing numbers.
- **The allowed exception is evaluation metrics,** which are outputs of the function. Both arms have them.
- **Residual leak: about one bit per apply.** Child IDs are content-addressed, so an apply that changed nothing yields a recognisable child. This is bounded by the `applies` budget. The harness flags C applies whose child bytes equal the parent's, and the report states how often this happened.
- **Only `layerdelta-agent` runs benchmark sessions** (the S4b headless runner). An MCP host such as an IDE agent has filesystem tools and could read `report.json` or the workspace, which closes Roadmap R2's last open item in the only way that works. The runner gives the model LayerDelta tools only. Each session runs against a fresh copy of the workspace, and the harness checks the trace for any route outside the arm's list.
- **Primary arms are class 1.** Raw values (class 2) are an exploratory third arm, run only with a local provider, and reported separately.

### 5.3 Tasks

Every task gives the agent a checkpoint, a dataset (exploration split only), an evaluator and a written goal ("raise mIoU on `shapes-seg` without lowering ..."). Trained base models come from seeded, CPU-only training scripts in `tools/bench/`, on the synthetic datasets and MNIST. Each is recorded by SHA-256.

Families (at least 3 required; 4 planned):

| Family | Base model | Dataset |
|---|---|---|
| classification | `ReferenceCNN` | MNIST |
| segmentation | the U-Net corpus family | `shapes-seg` |
| OCR | the CRNN corpus family | `glyph-ocr` |
| detection (if E3 detection lands in time) | the YOLO-style corpus family | `boxes-det` |

Task strata are pre-registered, so a result cannot hide where an advantage comes from:

| Stratum | What is wrong | Why it is there |
|---|---|---|
| **S-vis** planted, visible in statistics | k units of one closed group scaled by α, or given structured noise | Weight statistics should find it. A test of whether the agent *uses* them |
| **S-inv** planted, invisible in statistics | two units' input rows swapped in one member tensor only, breaking a coupling. Per-unit norms are unchanged | Statistics alone should not help, so W's edge here should be small |
| **S-nat** natural weakness | a confusion pair or a degraded condition: the v0.1 8→3 on blurred, a class with low IoU, a confusable glyph pair | Not planted. Closest to real use |

- **Planted faults are seeded.** A seed chooses the group, the units and the magnitude. The fault and its exact undo are recorded, which gives the score a ceiling.
- **Score.** Holdout recovery `R = (m_final − m_start) / (m_ref − m_start)`. R is not clipped: a harmful edit scores below 0.
  - `m_ref` for planted tasks is the unfaulted model.
  - `m_ref` for S-nat is the best result of a fixed scripted search. The search *chooses* its candidate on exploration, and the candidate is *measured* on holdout, so R cannot exceed 1 by selecting on holdout.
  - **Minimum gap.** A task instance whose `m_ref − m_start` on exploration is below a pre-registered minimum (planned: 0.05 absolute) is dropped **when it is generated**, before any session runs. This keeps the denominator away from zero without looking at results.
- **Guardrail.** Each task also has a guardrail metric, such as overall accuracy or mIoU on the other classes. A final child that breaks the guardrail by more than a pre-registered margin scores `R_guarded = min(R, 0)`. Both R and R_guarded are reported.

### 5.4 Protocol

1. **Pairing.** One task instance gives one session pair: same checkpoint, seed, budgets and prompt. The pair index decides which arm runs first (W first on odd indices).
2. **Sessions are independent.** Each has a fresh workspace and a fresh agent session. Exploration feedback (evaluate results) is the same machinery for both arms.
3. **Final answer.** The session ends with the runner's `final_child`. The harness then checks that the child exists, that its apply is in this session's trace, and its recipe hash. A session without a valid final child scores `R = 0` and is kept in the analysis (intention to treat).
4. **Holdout.** After the session ends, the harness runs `final-evaluations` on the frozen recipe hash with a human credential. The agent never sees holdout. The baseline and every final child use the same holdout samples.
5. **Infrastructure failures** (a crashed worker, a provider 5xx) rerun the pair once with the same seed, and are logged. Agent failures are results.

### 5.5 Size, analysis and controls

- **One primary contrast: ΔR = R_W − R_C on S-nat**, pooled over families. S-nat is the question users care about. The other two strata do a different job, and a pooled ΔR would be driven by the stratum mix:
  - S-vis favours W by construction, so it shows whether W *uses* the statistics;
  - S-inv is the negative control, where W's advantage should be small.

  Both are **descriptive**, at 12 pairs each (3 families × 4), which cannot detect 0.15.
- **N for the primary contrast**, for a two-sided α of 0.05 and 80% power to detect ΔR = 0.15:

  `n = ((1.96 + 0.84) · SD_d / 0.15)²`

  - SD_d = 0.32 gives n ≈ 36.
  - ITT puts failed sessions at R = 0, which makes R close to success or fail, so SD_d ≈ 0.5 is plausible. That gives **n ≈ 87 S-nat pairs**.

  N is set from the **upper 80% confidence bound** of the SD from the dry run, not from its point estimate, because a small dry run gives an estimate that under-sizes. The planned floor is 87 S-nat pairs plus 24 descriptive pairs, about **111 pairs (222 sessions)**. N never goes down, and it is frozen in the pre-registration before the live run.
- **Primary analysis.**
  - **Statistic:** the mean ΔR on S-nat, with a 95% bootstrap interval stratified by family (10,000 resamples).
  - **Secondary test:** a two-sided Wilcoxon signed-rank p with **Pratt's** handling of zero differences. ITT produces many ties, and Pratt's rule keeps them in the ranking.
- **Secondary analyses.** ΔR per stratum and per family, all descriptive. Cost per arm: applies, evals, tokens and wall time. A trace audit for W: the share of final edits whose units W read (stats, query or probe) before choosing them.
- **Controls gate the live run.** All three run with scripted agents and cost no provider calls:
  - **A/A calibration**: both arms are C with the same seeded random policy. The scripted policy costs nothing, so the full analysis is simulated on 1,000 A/A pairings at the pre-registered N. The share of intervals that exclude 0 must lie in [0.03, 0.07]. A single A/A interval missing 0 is expected 5% of the time, so it is not a gate.
  - **Positive control**: a scripted W that zeroes the highest-norm units of the most anomalous group, against a scripted C that picks a group at random. The interval must exclude 0 on S-vis. If it does not, the benchmark cannot detect an effect, and E8 stops and reports that.
  - **Dry run**: the full protocol with a local provider (loopback, no external calls) on a reduced N, to estimate variance and catch harness bugs.
- **Pre-registration.** The doc `docs/research/v0.5-benchmark-prereg.md` fixes the hypotheses, strata, task seeds, N, metrics, guardrail margins, analysis and exclusion rules. Its commit hash goes in the report. Any deviation is listed in the report as a deviation.
- **Report.** `docs/research/v0.5-benchmark-report.md` contains a per-session table, paired differences with intervals, the strata, costs, the controls, deviations and limits. It is internal (see non-goals).

## 8. Decisions and risks

- **Decisions this design makes** (reviewer may challenge):
  - datasets and preprocessing are declarative only;
  - NMS stays outside the model contract;
  - `eval:run` is a new capability;
  - a probe needs `weights:read`;
  - an activation intervention needs `weights:read`;
  - benchmark sessions run only in `layerdelta-agent`;
  - tools are absent from arm C's tool list **and** refused on the server;
  - the one primary contrast is S-nat.
- **Owner questions** (QUESTION.md):
  - **Q3**: the provider and model, the spend cap, and whether class-1 aggregates may go to a remote provider for the live run;
  - **Q4**: real datasets and their licences.

  Everything up to the dry run proceeds without an answer.
- **Risks.**
  - **R1 is the point of the benchmark.** The design protects the result's validity, not its sign. That is why it has strata, controls, intention to treat and pre-registration.
  - **Synthetic tasks may not transfer to real models.** That limits the scope of the claim (§5.1). Q4 widens it later.
  - **`.pt2` loading unpickles (§1 rule 3).** The residual risk equals the attach's own trust. The ATen interpreter is the documented fallback.
  - **CPU time on CI.** Evaluators run on tiny datasets in tests. The benchmark itself runs outside CI.
  - **GPU non-determinism.** Handled by V9's criterion.
  - **The planted S-vis stratum favours W by construction.** That is why the strata are reported separately. The pooled result is not the only headline.

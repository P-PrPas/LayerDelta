# v0.4 design: the agent surface (agent weight-space programming)

Status: **proposed** (AI Scientist), 2026-11-23. Owner decisions: Q1 option 3 and "agent surface first" ([QUESTION.md](../../QUESTION.md)). Builds on the v2 envelope and capabilities ([api.md](../reference/api.md)), inspect-ops rev6/rev7 ([inspect-ops.md](../reference/inspect-ops.md), [inspect-ops-rev7.md](../reference/inspect-ops-rev7.md)), edit programs and ops revision 2 ([edit-program.md](../reference/edit-program.md)), and the T5 trace. Target principles: [Architecture_Target §4](Architecture_Target.md).

## 0. Goal and non-goals

**Goal.** An agent, through any MCP host or through LayerDelta's own headless runner, can do weight-space work end to end. That means finding tensors and coupling groups, reading statistics, planning and applying edits, comparing children, and handing a human an auditable record. The agent stays within budgets the human set, and by default no tensor value leaves the machine.

**What already exists and stays authoritative.** All of the following live in the backend:
- the HTTP contract;
- capabilities (`model:read`, `weights:read`, `weights:write`);
- the apply quota and idempotency;
- the ID-only trace.

The bridge adds **no** authority of its own. It is a client with the agent token, and every check that matters happens in the backend, so a raw HTTP client cannot bypass anything the bridge enforces.

**Not in v0.4.**
- Evaluators and the benchmark (v0.5).
- Human editing UI (v0.6).
- A server-side workflow engine, which is rejected in §3.
- Agent-triggered graph attach or any code execution (Q1: user code runs only on a human action).

## 1. MCP bridge

### 1.1 Shape

- **Process:** `layerdelta-mcp`, a separate console script. It speaks MCP over **stdio** to the host and talks HTTP to the loopback backend, using the `connection.json` the backend writes (endpoint, project, agent token).
  - It holds no state beyond the session, and it never reads the workspace filesystem.
  - It never receives the human cookie.
- **Transport:** stdio only in v0.4. Streamable HTTP would add a second listening socket and its own auth story, so it waits until a host needs it.
- **Dependency (decision for PM):** the official `mcp` Python SDK, pinned, in an optional extra `layerdelta[mcp]`.
  - The alternative is a hand-written JSON-RPC 2.0 stdio loop of about 300 lines covering `initialize`, `tools/list` and `tools/call`.
  - I recommend the SDK. The protocol revises regularly (structured tool output and tool annotations are recent), and tracking it by hand is the bigger long-run cost.
  - The parity tests in §8 make either choice safe to swap later.

### 1.2 Tool table: one route, one client method, one tool

The tool table is **generated** from one route registry. It is not written by hand. Each registry entry has these fields:

```
{tool, method, path, capability, pure, human_only, input_model, idempotency, summary_fields}
```

From that one table:
- `AgentClient` methods are produced and checked;
- the MCP `tools/list` is built;
- the contract tests run (§8).

Human-only routes are filtered out by construction:
- graph attach and attach status;
- checkpoint import, export and upload;
- final evaluations;
- recipe import from file;
- session revoke, budget change, and proposal approve or reject.

| Tool | Route | Capability | Pure | Notes |
|---|---|---|---|---|
| `session_info` | GET /agent-session | (agent) | yes | capabilities, quota, budgets (§4), egress class (§6) |
| `list_checkpoints`, `get_checkpoint` | GET /checkpoints, /checkpoints/{id} | model:read | yes | get_checkpoint gains `parent` and `children` (lineage, §3) |
| `describe` | GET .../describe | model:read | yes | roles and groups when a graph is attached |
| `graph`, `graph_node`, `groups` | GET .../graph, .../graph/nodes/{id}, .../groups | model:read | yes | structure only, never values |
| `stats`, `query` | POST .../stats, .../query | weights:read | yes | aggregates |
| `diff` | POST .../diff | weights:read (+ `weights:values` for `values: true`) | yes | |
| `read_tensor` | POST .../read-tensor | **weights:values** (§6) | yes | raw values |
| `plan`, `validate` | POST .../plan, .../validate | weights:read | yes | dry run |
| `apply` | POST .../apply | weights:write | no | `key` required, creates a child, charges quota |
| `upload_blob` | POST /blobs | weights:write | no | base64 in MCP, 1 MiB per call cap in the bridge |
| `trace` | GET /trace | model:read | yes | own session only |

The legacy v0.1 run tools (`propose`, `run`, `status`, `compare`, `changes`, `cancel`) are exposed only with `--legacy-tools`. They are MNIST-only and are replaced by the v0.5 evaluator tools.

### 1.3 Results and errors over MCP

- **Results.** `structuredContent` is the HTTP response body, unchanged. That is the parity invariant: the same arguments give the same bytes after canonical JSON.
  - `content` adds one short text line built only from IDs and counts: "`stats` on `layer1.0.conv1.weight`: 16 units, truncated, pass `cursor` for more".
  - That text never echoes a tensor name or any other free text from the checkpoint (see §7).
- **Annotations.** `readOnlyHint` is true for pure tools; this is checked against `pure` in the registry, and the backend asserts `side_effects: []` for them. `apply` is marked `destructiveHint: false` (it creates a new checkpoint and never overwrites) and `idempotentHint: true` (with the same key).
- **Errors.** A backend error becomes a tool result with `isError: true` and `structuredContent = {error: {code, message, field, hint, retryable, status}}`, so the model can read it and correct itself.
  - Transport and protocol failures remain MCP protocol errors.
  - `hint` and `retryable` come from one **error catalog** (§2.3); the backend's `{code, message, field}` is never rewritten.
- **Size guard.** The bridge refuses a result larger than `--max-result-bytes` (default 200 KB) with `result_too_large` and a hint naming the argument to lower (`limit`, `max_elems`). It never truncates silently. The schema defaults in §2.2 keep this rare.

## 2. Schemas tuned for LLM use

### 2.1 Input schemas

- Generated from the same pydantic request models (`extra=forbid`), so an unknown field is refused, as it is over HTTP.
- No deep `oneOf` or `anyOf` at the top level. Two tools need a union:
  - **Selectors** are one `select` object whose `description` lists the three forms (tensor-local, group, `resolved.selector` passthrough), with an `examples` entry for each.
  - **`plan`, `validate` and `apply`** take either `program` + `hypothesis` or `recipe`. The tool description says "exactly one", and the backend error says which field is wrong.
- Every enum is spelled out:
  - roles;
  - stat names;
  - `op` names;
  - group `kind`;
  - boundary `reason`;
  - error `code`s that the tool can return.
- Each tool description is at most 600 characters and follows one pattern: what it does, when to use it, what it costs (budget dimension, §4), and the next tool to call with which field ("pass `matches[0].selector` to `plan`").

### 2.2 Defaults and output shaping

- **Explicit defaults.** The bridge sends every default explicitly, so the parity test compares like with like. LLM-sized defaults are part of the tool schema, not hidden in the bridge:

  | Tool | Argument | MCP default |
  |---|---|---|
  | `describe` | `limit` | 200 |
  | `graph` | `limit` | 200 |
  | `groups` | `limit` | 50 |
  | `read_tensor` | `max_elems` | 256 |
  | `stats` | `limit` | 64 |
  | `diff` | `limit` | 64 |
  | `query` | `limit` | 20 |

  The HTTP caps stay as they are.
- **IDs as handoffs.** `selection_id`, `group_id`, `recipe_hash` and child `checkpoint_id` are always top-level in the result where they exist, so the model copies an ID rather than rebuilding a selector.

### 2.3 Error catalog

`docs/reference/errors.md` is generated from one table in code: `{code, http_status, retryable, hint}`. It covers every `InspectError` code and every route `fail()` code.

Examples:

| Code | Retryable | Hint |
|---|---|---|
| `group_not_closed` | no | `permute_units` needs a closed group; list closed groups with `groups(closed=true)`; other ops are allowed on open groups |
| `cap_exceeded` | no | narrow the selection or lower `limit` |
| `budget_exhausted` | no | stop and report; the user sets budgets |
| `quota_exhausted` | no | the apply quota is used up |
| `no_graph` | no | a human must attach a graph; agents cannot |
| `forbidden` | no | report the missing capability; do not look for another path |

A contract test fails when a code that the code base can raise is missing from the catalog.

## 3. Composable workflows

Composition comes from **IDs and re-submittable resolved inputs**, not from a server-side workflow engine. A workflow engine would be a second program language, and it would hide steps from the trace. What already composes:

- query → plan: `query.matches[].selector` (tensor or group) goes straight into a program `select`.
- plan → apply: `plan.result.recipe` is sent back as `recipe`, so apply runs exactly what was planned (same `recipe_hash`).
- apply → next step: the child `checkpoint_id` becomes the next base. `diff(child, parent)` checks the change, and the trace links the apply to the reads that motivated it.

Gaps closed in v0.4:
1. **Lineage.**
   - `get_checkpoint` returns `parent`, `recipe_hash` and `children` (IDs only).
   - Without lineage, an agent cannot get from a child back to its parent after a restart.
2. **Apply result points at what to verify.**
   - The apply result echoes `diff_hint: {checkpoint_id: parent, other: child, selector}`.
   - The `selector` is the union of the program's `select` entries, as an explicit list, so "apply then verify" is one copy.
   - This is additive and only appears in apply results.
3. **The cookbook documents canonical sequences** (§7): find, inspect, plan, apply, verify; compare two children; undo by re-applying from the parent.

## 4. Per-session read and write budgets

Budgets are metered and refused **in the backend**, per agent session (one server process = one session, as in the trace). The human sets them at start: `--agent-budget values=…,scan=…,applies=…,blob_bytes=…`. They are reported by `session_info`.

| Dimension | Charged by | Unit |
|---|---|---|
| `values` | `read_tensor`, `diff` with `values: true`, group read | elements returned |
| `scan` | `stats`, `query`, `diff`, group stats, `plan`/`validate` (the elements an op reads) | elements read from the file |
| `applies` | `apply` (the existing quota, unchanged) | children created |
| `blob_bytes` | `upload_blob` | bytes |

Rules:
- **Charge before the result.** The cost is known after the selector resolves and before any data is read. If the remaining budget is smaller than the cost, the call is refused with `budget_exhausted` (429, `field` = the dimension), and nothing is read.
- **Replays are free.** A replay of an idempotent request costs nothing, as for the quota today.
- **Reported outside the body.** Usage goes in response headers (`LayerDelta-Budget: values=…;scan=…`), so v1 envelopes stay byte-identical. The bridge copies the headers into the MCP result `_meta`. Every charge is written as a trace field.
- **The agent cannot raise a budget.** Only the human can lower or raise it from the Desktop session viewer (S5), and every change is a trace event.

## 5. Trace and supervision

- **Trace (extend T5).**
  - Each event gains `tool` (the registry name, the same for HTTP and MCP calls), `via` (`http` | `mcp`) and `budget_charged`.
  - It remains ID-only: no values, names or texts.
  - The T5 link from an apply to its plans and selections stays the core audit question: "which reads led to this child?"
- **Kill switch.** A human-only route, `POST /agent-sessions/{session}/revoke` (the target session is in the path; budget changes use `POST /agent-sessions/{session}/budget`, and the approval gate uses `GET /proposals` and `POST /proposals/{id}/approve|reject`; route names agreed on PR #45). After it, every agent call answers `session_revoked` (401). The Desktop offers it beside the session timeline.
- **Session viewer (Desktop, supervision only, per Q2).** It shows:
  - the timeline from `GET /trace`;
  - budget gauges;
  - each apply with its plan, the reads that motivated it, and a `diff` link;
  - revoke.

  It is read-only apart from budget changes and revoke.
- **Approval gate** (option, decision for PM). With `--agent-apply-requires-approval`:
  - an agent's `apply` returns `202 {proposal_id}` and creates nothing;
  - the human approves in the viewer, which runs the same recipe as a human-confirmed apply under the same idempotency key.

  I recommend building it in S5, with the default off.

## 6. Provider adapters and the outbound data policy

There are two places data can leave the machine:
1. **An external MCP host.** The host's model provider sees every tool result. LayerDelta cannot filter what the host forwards, so the control has to be **what the backend releases to the token**.
2. **LayerDelta's own headless runner** (`layerdelta-agent`, used for the cookbook and the v0.5 benchmark). Here LayerDelta also owns the provider call.

**Data classes.** Classes 0 to 2 are what the backend releases. Class 3 is the inbound direction.

| Class | Contents | Released when |
|---|---|---|
| 0 | metadata: IDs, names, dtypes, shapes, roles, groups, boundaries, coverage, trace | always (`model:read`) |
| 1 | aggregates: stats, query rankings, diff summaries, plan effect counts | `weights:read` |
| 2 | values: `read_tensor`, diff `values: true`, group reads, legacy activation maps and images (R2) | new capability **`weights:values`** |
| 3 | inbound: blobs, programs | `weights:write` |

- **Splitting `weights:values` out of `weights:read`** is the one contract change.
  - Existing tokens with `weights:read` keep values unless the operator passes `--agent-no-values`. That keeps v0.2 compatibility.
  - **The bridge defaults its own token request to class 1:** `connection.json` records the egress class the human chose, and the backend refuses class-2 tools for it with `forbidden`.
  - Values for a remote model are an explicit human choice, recorded in the session and shown in the viewer.
- **The headless runner applies the same classes per provider:**
  - local providers (loopback endpoints such as llama.cpp or Ollama) may use class 2 if the token has it;
  - remote providers (Anthropic Messages API, OpenAI-compatible) default to class 1.

  The adapter interface is `send(messages, tools) -> tool_calls | text`. It has no access to the workspace, and it sends only tool results the token already received.
- **Refuse, never redact.** A class the session may not see is refused with `forbidden` and a hint. Responses are never edited in flight, which keeps behaviour predictable for the model and keeps parity exact.

## 7. Agent cookbook (scope)

`docs/guides/agent-cookbook.md` plus runnable scripts in `examples/agent/`. Each recipe is a deterministic script run in CI against the T6 corpus, with no LLM.

1. **Orient:** `session_info`, `list_checkpoints`, `describe`, `groups(closed=true)`.
2. **Find weak units and zero them through a group:** `query` (L2 rank on a group) → `plan` → `apply` → `diff`, with BatchNorm statistics left in or out through `members`.
3. **Function-preserving permutation:** `permute_units` on a closed group. The script then checks equivalence with a forward pass outside LayerDelta.
4. **Compare two children** of the same parent, and walk lineage.
5. **Recover from errors:** `group_not_closed`, `cap_exceeded`, `budget_exhausted`, a lost apply response (same key).
6. **Hand-off report:** what to give the human (recipe hashes, child IDs, trace sequence numbers, plan effects).

Plus a section on **untrusted text**. Tensor names, module paths, hypotheses and recipe text come from files and other sessions. They are data and never instructions. The bridge keeps them out of the `content` text, but they still appear in `structuredContent`.

## 8. Acceptance tests

The Roadmap's "G12/G13 generalized" is not defined in the current docs. T5 and T7 below replace it with explicit tests.

| # | Test |
|---|---|
| T1 | **Parity.** For every tool, a recorded script of valid and invalid calls gives an MCP `structuredContent` equal to the HTTP body (canonical JSON), including error `code`/`field` and status mapping. |
| T2 | **Tool-schema contract.** <br>• `tools/list` equals the registry filtered to agent routes. <br>• No human-only route appears. <br>• Every schema rejects unknown fields, and every documented example validates. <br>• `readOnlyHint` holds iff `side_effects` is always `[]`. <br>• A snapshot of the schemas changes only together with a version bump. |
| T3 | **Error catalog.** Every code the code base can raise has an entry. `isError` results carry `hint` and `retryable`. |
| T4 | **Budgets.** <br>• Each dimension refuses at its limit before reading. <br>• Replays are free. <br>• Headers and `session_info` agree. <br>• HTTP and MCP consume identically. <br>• An agent cannot change a budget. |
| T5 | **Trace (generalized G12).** <br>• Every MCP and HTTP call is one event with `tool` and `via`. <br>• Every child links back to the plan and selections that motivated it. <br>• A scan of all events finds no tensor value, name or free text. |
| T6 | **Egress.** <br>• With a class-1 session, a property test over every tool and fuzzed arguments finds no element array from a tensor in any result. <br>• Class-2 tools answer `forbidden`. <br>• The headless runner with a recording stub provider sends nothing outside the session's class. |
| T7 | **Scripted agent (generalized G13).** A deterministic MCP-stdio client completes cookbook recipes 2 and 3 on three families (ResNet, ViT, CRNN) through the bridge alone. It stops at the user budget even while the server quota remains, and its final report lists only children that exist. |
| T8 | **Supervision.** <br>• Revoke stops the next call with `session_revoked`. <br>• With the approval gate on, an agent apply creates nothing until a human approves, and the approved child equals a direct apply of the same recipe. |
| T9 | **Live smoke (manual, not CI).** One real MCP host (for example Claude Code) completes cookbook recipe 2 on one family. The transcript is attached to the PR. |

## 10. Decisions requested and risks

**Decisions for PM:**
1. The `mcp` SDK as an optional pinned extra (recommended), or a hand-written stdio loop.
2. `weights:values` as a separate capability. Existing tokens keep values unless the operator passes `--agent-no-values`. The bridge defaults to class 1.
3. Whether the approval gate (§5) is in v0.4 (recommended, default off).

**Risks:**
- **Hosts handle structured output unevenly.** Mitigation: the `content` text line in §1.3, and an output-size guard.
- **Prompt injection through tensor names.** Mitigation: names stay in structured data only, and §7 covers it.
- **The core assumption is untested.** The Roadmap still notes no evidence that weight tools help agents. v0.4 builds the surface that v0.5 measures, and T7 shows only that the surface works, not that it helps.
